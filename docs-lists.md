# Lists and MCP

The single public `/lists` page reads Supabase Postgres through Drizzle. It shows a flat feed sorted by the time the rating last changed (not by note edits), with unrated entries after rated entries. Search uses `?q=...`; list types use repeated `?type=movies&type=places` parameters. Search and filters combine, are case-insensitive, and work with native GET forms without JavaScript. They match names, reviews, tags, details, and type names. The shared header uses exactly the homepage's container, height, typography, and navigation. Search, buttons, the filter popover, and enhanced checkboxes use shadcn/ui primitives with semantic monochrome tokens. A native details/checkbox fallback keeps filters usable before hydration and without JavaScript.

`/lists.md` and `Accept: text/markdown` use the same filtered feed and ordering. Previous `/lists/[slug]` links redirect to the single feed with that type selected; unknown types in old paths still return 404. Responses read current data without a shared content cache, so saved MCP edits appear on the next request.

## Configuration

Vercel Marketplace supplies `POSTGRES_URL` (pooled, used by the application) and `POSTGRES_URL_NON_POOLING` (used by migrations). Keep both server-only. The `postgres` driver disables prepared statements for transaction-pooler compatibility.

Set `LISTS_OWNER_PASSWORD` in the Vercel project's Production environment to a unique password of at least 24 characters, ideally generated by a password manager. Do not put it in Git or send it in chat. Owner authorization fails closed when this variable is missing. No email codes, public registration, or Supabase Auth configuration is required.

`LISTS_OAUTH_ISSUER` defaults to `https://zacowan.com`. For local development or a preview you intend to connect an MCP client to, set it to that deployment's exact origin and use a separate owner password.

For local development, connect database credentials to Development in Vercel and pull them into `.env.local`. A separate development/preview database is recommended. Never point experiments at production data unintentionally.

## Migrations and verification

```sh
pnpm db:generate  # generate a checked-in SQL migration after schema changes
pnpm db:migrate   # apply checked-in migrations, loads .env.local when present
pnpm db:verify    # explicit real-database integration verification
pnpm typecheck
pnpm test
pnpm build
```

Apply migrations once before deploying code that requires them. Do not migrate at request time. The initial migrations create only new tables and enable row-level security with no anonymous/authenticated API policies: browser clients cannot query or mutate them through Supabase's public API. Server queries use the database role. `db:verify` creates temporary content, tests real queries and OAuth/MCP behavior, then deletes its content and OAuth grants in a finally block. Do not run it as an application request or on every production deployment.

## Connect an MCP client

Use Streamable HTTP at `https://zacowan.com/mcp` with OAuth. In ChatGPT, add a custom app/MCP connection (developer mode may be required), supply that URL, and select OAuth. The client discovers the authorization server, registers its callback, and opens the owner authorization screen. Enter the owner password there and approve the displayed client and callback. Approval grants read/write access to public lists. Changes publish immediately.

OAuth uses PKCE S256, exact registered redirect URIs, signed consent and an HttpOnly CSRF cookie, short-lived one-use codes, hashed opaque bearer/refresh tokens, refresh rotation, token revocation, and database-backed rate limits. Access tokens last one hour; refresh tokens last 30 days. No database or owner password is returned to MCP clients. `/api/lists/oauth/revoke` accepts a token for revocation. To disconnect every client, delete rows from `lists_oauth_grants` in an administrative SQL session.

Available tools: `get_lists`, `get_list`, `create_list`, `update_list`, `add_entry`, `update_entry`, `get_entry_history`, `restore_entry`.

Example requests:

- “Create a Movies list.”
- “Add Arrival to Movies, 9 out of 10, with my note: …”
- “Archive that entry.”
- “Restore its previous review.”

The tool must use only ratings/reviews supplied by the owner. Ratings accept 0–10 in half-point increments, or null for unrated. Internally integer half-points avoid floating-point ambiguity; HTML shows the exact equivalent on a five-star scale (8.5/10 = 4.25 stars) plus the numeric score. Tool responses always return the 0–10 scale.

Entries have stable UUIDs, dates, tags, short text metadata, URLs restricted to HTTP(S), and optimistic version checks. A unique operation UUID makes retries idempotent; a successful entry edit creates an immutable revision in the same transaction. Archive instead of deleting; use history and restore for undo. Lists start empty, with no invented ratings or sample reviews.
